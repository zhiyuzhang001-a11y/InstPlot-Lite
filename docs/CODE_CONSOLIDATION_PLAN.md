# InstPlot Lite 代码整合建议

## 目的

本文件用于指导 InstPlot Lite 后续的代码结构整理。整合的目标是降低维护成本、减少重复代码，并让新增功能更容易定位和测试，而不是重新设计现有功能。

整合过程中必须遵守以下原则：

1. **用户可观察到的行为保持不变。** 不借结构整理修改计算结果、操作流程、窗口行为、默认值、文件格式或文案。
2. **算法和界面分开整理。** 已经位于独立 crate 中的数据读取、导出、拟合和处理算法不迁回应用层。
3. **小步迁移。** 每次只抽取一个职责，单独提交并通过完整检查；不一次性重写 `app.rs`。
4. **先建立测试，再移动高风险代码。** 对现有测试没有覆盖的行为，先补充结果导向的测试。
5. **不为减少文件数量而合并代码。** “整合”指明确职责和统一公共逻辑，不是把更多内容放进同一个大文件。
6. **不在本轮调整 UI 设计。** 颜色、字号、间距、布局和交互优化应作为后续独立工作进行。

## 当前结构判断

项目已经把核心能力拆分为独立 workspace crate：

- `instplot-core`：数据模型。
- `instplot-io`：数据导入与导出。
- `instplot-fitting`：拟合算法和公式计算。
- `instplot-processing`：数据处理算法。

这一层划分是合理的，应继续保留。

当前主要维护压力集中在 `src/app.rs`。该文件超过 4,000 行，同时包含：

- 应用全局状态；
- 文件导入和导出流程；
- 数据处理窗口；
- 曲线拟合窗口；
- 主工具栏、数据侧栏和绘图区；
- 小窗口的原生/嵌入显示、置顶和关闭逻辑；
- 坐标轴、图例和数值格式化；
- 界面样式；
- 单元测试。

这些职责互相耦合，使得局部修改更难确认影响范围。代码整合应优先解决这个问题，而不是重写已经稳定的算法 crate。

## 建议的目标结构

目标结构可以根据 Rust 借用关系微调，但职责边界应保持如下：

```text
src/
├── app.rs                    # InstPlotLiteApp、生命周期和各模块协调
├── app/
│   ├── state.rs              # 不需要被 UI 导入的应用协调状态及默认值
│   ├── import.rs             # 文件选择、载入和导入后的状态同步
│   ├── export.rs             # 应用层导出流程，不包含底层文件编码
│   ├── processing.rs         # 数据处理动作与应用状态的连接
│   ├── fitting.rs            # 拟合动作与应用状态的连接
│   └── screenshot.rs         # 截图请求、结果接收和图片保存协调
├── ui/
│   ├── mod.rs
│   ├── main_view.rs          # 顶部工具栏、侧栏、状态栏和主布局
│   ├── plot.rs               # 绘图、图例、坐标交互和可见性
│   ├── tool_window.rs        # 小窗口公共壳、滚动、关闭、置顶和嵌入判断
│   ├── delete_confirmation.rs # 删除确认界面，只返回确认/取消操作
│   ├── export_window.rs      # 导出窗口内容
│   ├── processing_window.rs  # 数据处理窗口内容
│   ├── fitting_window.rs     # 曲线拟合窗口内容
│   ├── formatting.rs         # 坐标轴、公式、图例和紧凑文本格式化
│   └── theme.rs              # 现有样式配置；本轮只迁移，不改变视觉值
├── session.rs                # 与 UI 无关的会话结果，如拟合 overlay 和来源关联
├── data.rs                   # 对 instplot-core / instplot-io 的薄封装
├── data_export.rs            # 对 instplot-io 导出接口的薄封装
├── fitting.rs                # 对 instplot-fitting 的薄封装
├── processing.rs             # 对 instplot-processing 的薄封装
├── edit_history.rs
├── image_export.rs
├── updater.rs
├── fonts.rs
└── main.rs
```

不要求一次建立所有文件。如果某个拆分只会制造循环依赖或大量公开字段，应先保留在 `app.rs`，待公共接口稳定后再移动。

### 模块依赖和 UI 操作规则

模块必须保持 `app → ui` 的单向调用关系：

- `app` 层可以调用 `ui` 层和算法 crate；
- `ui` 层不能导入、持有或直接修改完整的 `InstPlotLiteApp`；
- `ui` 函数只接收绘制所需的最小可变状态、只读数据或轻量只读 view model；
- 用户操作由 `ExportAction`、`ProcessingAction`、`FitAction`、`DeleteAction` 等明确命令返回；
- `app` 在 egui 绘制闭包结束、相关借用释放后执行命令，再修改数据、历史、拟合结果和状态文本；
- 同时供 `app` 和 `ui` 使用、且不含 egui 行为的会话类型放在中立模块中，不能为了共享而让 `ui` 反向依赖 `app`。
- UI 局部状态和 Action 类型可以定义在对应 `ui` 模块中并由 `app` 持有；应用持久结果放在 `session.rs`；只属于协调层的状态放在 `app/state.rs`。
- UI 可以读取核心数据类型，但文件对话框、文件写入、算法执行、历史记录和持久状态修改只能发生在 `app` 层。

当前数据处理窗口已经使用“闭包内生成请求、闭包后调用 `apply_processing`”的方式，可以作为其他窗口迁移的参考。不能通过扩大大量字段的可见性来绕过边界，也不能让 UI 函数接收 `&mut InstPlotLiteApp`。

同样的规则也适用于主界面和绘图区：主界面返回 `MainAction`，绘图区返回包含选择、删除请求和可见区域等信息的 `PlotResponse`，由 `app` 在绘制结束后统一写回。这样可以避免为了拆文件而复制数据，或在 egui 闭包中同时可变借用多个应用字段。

## 状态组织建议

`InstPlotLiteApp` 目前保存多个功能域的字段。建议逐步组合为状态对象，但不要一次性改变所有字段：

```rust
struct InstPlotLiteApp {
    data: DataViewState,
    plot: PlotState,
    processing: ProcessingUiState,
    fitting: FittingUiState,
    fit_results: FitResultState,
    export: ExportUiState,
    editing: EditingState,
    status: String,
    // updater 等平台状态继续按 cfg 保留
}
```

建议的职责：

- `DataViewState`：数据集、当前数据集、X/Y 列选择。
- `PlotState`：视图范围、重置请求、选择坐标、绘图区矩形和截图状态。
- `ProcessingUiState`：窗口打开状态、作用范围、参数和多选状态。
- `FittingUiState`：窗口打开状态、拟合设置、选择和窗口提示。
- `FitResultState`：位于中立的 `session.rs`，保存拟合 overlay、目标数据集 ID、X/Y 列关联及持久结果；关闭拟合窗口不得清除它。
- `ExportUiState`：窗口状态、格式、数据集和列选择。
- `EditingState`：撤销/重做历史、待删除点和框选状态。

状态对象只负责保存状态和简单一致性操作。数据处理与拟合算法继续通过现有 crate 调用，不能复制到 UI 模块。

## 优先统一的重复逻辑

### 1. 工具窗口公共壳

数据处理、曲线拟合和数据导出应共用一套轻量窗口框架，统一负责：

- 原生窗口与嵌入窗口的选择；
- 唯一且稳定的窗口 ID；
- 已打开窗口再次点击时置顶；
- 关闭状态同步；
- 主窗口全屏以及 Windows 最大化判断。

各功能模块只绘制自己的内容，不能自行重复实现窗口生命周期。窗口特有的尺寸、滚动 ID、最小尺寸和内容间距仍由各窗口自己声明，不把公共层扩展成包含所有选项的“万能窗口组件”。

### 2. 选择状态

拟合、数据处理和导出都有“当前数据集/选定数据集”的概念。可以共享安全的选择辅助函数，例如：

- 数据集数量变化时同步布尔选择数组；
- 全选、全不选；
- 获取唯一选中项；
- 禁止空选择执行操作。

各功能的业务语义仍应分开。例如拟合和数据处理的作用范围不应因为复用控件而变成同一个状态。

### 3. 显示格式化

坐标轴刻度、工程计数法、拟合公式、参数、图例名称和长文件名截断应集中到纯函数模块。这些函数应尽量不依赖 `egui`，便于通过输入/输出单元测试验证。

### 4. 应用层错误与状态消息

文件错误、公式错误和处理结果可以统一返回应用层可显示的结果类型，但不应在结构整理阶段重写现有中文提示。先迁移原文，后续文案优化单独处理。

## 分阶段执行顺序

### 阶段 0：建立行为基线

- 记录当前测试数量和通过结果。
- 保存典型文件的导入、拟合、处理和导出结果作为 fixtures。
- 确认 Windows 安装包与更新器的真实结果测试仍在 CI 中运行。
- 记录 macOS 普通窗口/全屏、Windows 普通窗口/最大化下的小窗口行为。

完成标准：没有源码结构变更，仅形成可重复的行为基线。

### 阶段 1：抽取显示格式化纯函数

- 移动坐标轴、图例和紧凑文本格式化函数。
- 保持函数签名和测试样例不变。

风险较低，适合作为第一次结构提交。

### 阶段 2：统一工具窗口基础设施

- 抽取窗口模式判断、ID、置顶、关闭和滚动容器。
- 依次接入数据处理、曲线拟合和数据导出窗口。
- 每接入一个窗口即运行测试，不同时迁移三个窗口。

这是最值得优先完成的部分，因为它能减少跨平台窗口问题重复出现。

### 阶段 3：拆分三个功能窗口

- 先迁移导出窗口，再迁移数据处理窗口，最后迁移拟合窗口。
- 窗口模块负责展示和收集用户输入。
- `app` 层负责调用算法、写入数据、更新历史和状态文本。

推荐按上述顺序，是因为拟合窗口与主图 overlay 的联系最多，最后迁移更安全。

### 阶段 4：拆分导入和辅助流程

- 将文件选择、载入、重复 ID 检查和导入后的列选择同步放入明确的导入工作包。
- 删除确认界面只返回确认或取消操作，实际删除与历史记录仍由 `app` 执行。
- 截图请求、截图事件处理与 PNG 写入协调归入截图应用模块；底层图片编码继续由 `image_export.rs` 负责。

导入、删除确认和截图应分别提交，不能因为同属“辅助流程”而混成一次大改。

### 阶段 5：分步拆分主界面和绘图区

- 先原样迁移主题、工具栏、数据侧栏和状态栏。
- 再抽取绘图系列构建和拟合 overlay 展示。
- 最后抽取图例可见性、缩放、平移、点选、框选和删除请求。
- 保持绘图系列 ID 不变，避免隐藏/显示状态在刷新后丢失。

每一步单独提交并运行验证，不能把主布局、所有绘图交互和图片导出一次性迁移。

### 阶段 6：按收益决定是否组合应用状态

- 在前述模块边界稳定后，仅在确实减少耦合且没有制造复杂借用关系时，才逐组组合 `InstPlotLiteApp` 字段。
- 每次只组合一个功能域。
- 不为了消除借用错误而使用全局可变状态或不必要的 `Rc<RefCell<_>>`。

状态组合是条件性目标，不为了满足示例文件树而强制执行。完成后，`app.rs` 应主要保留初始化、事件协调和 `eframe::App` 实现。

## 每个阶段禁止顺便修改的内容

- 数学公式、拟合算法和参数默认值；
- 数据处理覆盖/保留规则；
- 导入文件解析和多数据段关联规则；
- 导出文件内容、列顺序、命名和覆盖策略；
- 拟合曲线与原始数据的关联方式；
- 图例点击后的曲线和数据点同步隐藏规则；
- 坐标轴刻度与科学计数法规则；
- 撤销/重做边界；
- Windows 更新、安装、重启和 OSS 发布流程；
- UI 颜色、字号、间距、控件名称和布局。

如确实发现缺陷，应单独记录并在独立提交中修复，不能混入“仅重构”提交。

## 验证要求

每个整合提交至少运行：

```sh
cargo fmt --all -- --check
cargo test --workspace --locked
cargo clippy --workspace --locked --all-targets --all-features -- -D warnings
cargo build --release --locked --package instplot-lite
```

此外必须验证实际结果，而不能只依据命令退出码或日志文字：

- 同一文件重构前后导入的数据集、列、行和数值一致；
- 代表性处理操作产生完全相同的数值结果；
- 代表性拟合产生相同的公式、参数、R² 和 overlay 点；
- 单文件、多文件、组合和分开的文本导出在规范化换行后内容一致；
- XLSX 重新导入后的工作表、列、行、数值和拟合关联一致，不依赖整个压缩文件哈希；
- 导出的拟合数据重新导入后仍能与原曲线正确关联；
- 隐藏曲线后执行处理、拟合、撤销或重做，不会让其他曲线意外重新显示；
- 三个工具窗口可同时存在，拥有不同 ID，关闭其中一个不影响其他窗口；
- Windows 最大化使用嵌入窗口，Windows 普通模式使用原生窗口；
- macOS/Linux 的现有窗口模式不变；
- 小窗口缩小时仍可滚动到全部内容；
- 图片导出结果不包含应用控件，且坐标、图例和曲线不发生变化。

涉及平台窗口行为的改动不能只在 macOS 上以模拟变量验证。现有 GitHub Actions 可以验证 Windows 编译、安装和更新流程，但不会真实操作 GUI，也不能证明最大化、多窗口、置顶或拖动行为正确。因此应采用三层验证：纯判断逻辑由单元测试覆盖，Windows CI 负责构建和既有安装/更新检查，窗口实际表现由真实 Windows 人工验收。只有将来增加可靠的 GUI 驱动或截图断言后，才能将第三层称为 CI 自动验收。

## 提交策略

- 一个提交只完成一个结构目标，例如“抽取格式化模块”或“统一工具窗口壳”。
- 纯移动与行为修改不能放在同一个提交中。
- 文件移动尽量保持代码内容不变，以便 Git 正确识别历史。
- 每个提交说明移动了什么、哪些行为明确没有变化、运行了哪些检查。
- 未完成某一阶段时不发布新版本；纯内部整理通常不需要单独 Release。
- 如果整合造成回归，可以按阶段回退，不需要撤销整个计划。

## 完成标准

代码整合完成需要同时满足：

- `app.rs` 只承担应用生命周期和模块协调，不再包含三个完整工具窗口的绘制实现；
- 数据处理、拟合、导出窗口共用工具窗口基础设施；
- 格式化逻辑可以脱离完整应用状态单独测试；
- `app → ui` 依赖方向明确，UI 不反向依赖完整应用类型，也不直接执行文件或算法副作用；
- 没有引入新的全局可变状态、重复数据副本或明显内存开销；
- 全部自动测试、Clippy、格式检查和发布构建通过；
- 既定行为基线一致，自动测试全部通过，真实平台验收未发现变化；
- 用户操作流程、界面视觉和导入导出结果未发现变化。

完成上述结构工作后，再单独制定 UI 简化方案。这样出现问题时，可以明确判断是结构迁移还是视觉/交互调整导致的。
